# 上传链路统计与体验优化建议

## 当前判断

- 线上数据库中，真实未完成的上架批次记录只有 53 条；没有查到 15380 或 16445 对应的服务端上传中记录。
- 页面显示从 16445 跳到 10/15380，说明至少有两类数据源在竞争：初始本地状态/旧总数，以及接口刷新后的总数。
- 当前 `GalleryManager` 把 `total`、`assets`、`page` 作为多页面共用状态；待上传、上传中、已上传、精品图库切换和静默刷新都写同一组状态，容易出现“当前页是上传中，total 却来自别的列表”的错位。
- 上传中页面同时承担本地恢复缓存、云端批次、对账统计、自动恢复任务、手动停止删除五件事，状态口径不够单一。

## 建议一：先修统计口径

目标：上传中只展示真实上传中数量，不再显示待上传总数或旧缓存总数。

- 为每个图库页签拆独立列表状态：`pendingTotal`、`processingTotal`、`uploadedTotal`、`featuredTotal`，不要共用一个 `total`。
- 上传中顶部数字优先使用 `/gallery/listing-reconciliation` 的 `processingCount`；列表分页总数只作为表格页码，不作为“上传中商品”主指标。
- 进入上传中页时先显示“正在刷新”，不要先显示上一次页签残留总数。
- 静默刷新如果接口没有返回 `total`，不能沿用旧 `total`；应保留当前页签自己的上一次 `processingTotal`，或直接不更新总数。
- 增加前端调试日志：记录每次 `loadAssets` 的 `sourceTab`、`listingStatus`、`includeTotal`、`result.total`、`nextTotal`，排查类似跳数问题。

## 建议二：上传链路分成三步

目标：让用户知道自己现在在做“上传图片”“准备商品”“提交 Ozon”哪一步。

- 图片上传页：只负责选本地图片、选择商品类型/比例、上传到云图库。
- 待上传页：只负责筛图、套图、标题、选择店铺模板、创建上架批次。
- 上传中页：只负责查看批次进度、恢复失败/中断任务、停止并释放图片。
- 已上传页：只展示已经提交到 Ozon 或确认完成的记录。

## 建议三：把配置前置成向导

目标：减少每次上传前重复配置模板。

- 新增“上架配置向导”：商品类型与比例 → 样机模板 → 标题模板 → 店铺 → 商品模板 → 仓库/活动/价格。
- 每个店铺显示配置完整度，例如“缺商品模板”“缺本地 Ozon 模板”“缺仓库”。
- 保存为“上架方案”，上传时只选择方案，不再在待上传列表里反复配置。
- 模板选择做成共享模板优先、当前店铺模板其次、其他店铺模板折叠显示。

## 建议四：上传中任务管理优化

目标：上传中不再像“黑盒”。

- 按批次展示任务，而不是只按图片展示：批次卡片包含店铺、商品数、阶段、失败原因、操作按钮。
- 批次阶段统一为：待套图、套图中、待标题、标题中、待提交、提交中、已完成、失败。
- 每个批次提供明确操作：继续、暂停、停止并释放、查看日志、查看失败项。
- 失败项支持只重试失败图片，不要每次批量恢复全部。

## 建议五：数据一致性保障

目标：云端、客户端、本地缓存三方一致。

- 云端批次状态作为唯一权威状态；本地缓存只做临时恢复辅助，不能决定主统计。
- 每次创建批次时保存完整配置快照，后续不依赖当前页面配置变化。
- 本地助手提交成功后必须回写云端完成状态；失败要回写失败原因和阶段。
- 增加“上传链路自检”接口：统计待上传、上传中、已上传、孤儿缓存、未完成批次、运行中本地任务。

## 推荐落地顺序

1. 修复 `10/15380` 统计错位：拆页签总数 + 上传中主指标改用对账 `processingCount`。
2. 增加上传链路自检面板：先让异常数据可见。
3. 改造上传中为批次视图：图片明细作为批次下钻。
4. 增加上架配置向导和方案保存。
5. 优化失败重试和停止释放逻辑。
